# 0015. Two independent controls replace the Terraform allocation guard

- Status: accepted
- Date: 2026-10-14
- Note 2026-11-03: [ADR 0029](0029-plain-tfvars-files-replace-the-config-wrapper.md) replaces the deployment wiring of this ADR. The deployer sets `grant_billable_provisioning` for each stack in the git-ignored `terraform.tfvars`, and its default stays `false`. The decisions of this ADR stay.

## Context

[ADR 0010](0010-one-experiment-file-of-modules-and-jobs-with-a-billable-guard.md) section 7, amended by [ADR 0011](0011-store-and-per-job-simulate-replace-run-mode.md) section 3 rule 4 and section 7 item 7, decided that each Terraform stack reads the same experiment file as its prober and refuses to plan an active, unconsented allocation entry: a `terraform_data.allocation_guard` resource, with a `lifecycle { precondition }`, re-implements the prober's own per-job consent check (`allow_allocation`, `simulate`) in HCL, over the raw YAML the file holds.

Building this guard surfaced a problem the 2 ADRs did not anticipate: OpenTofu's `yamldecode` and the prober's PyYAML loader resolve a YAML scalar's type differently, and the 2 implementations drift apart on exactly the question the guard exists to answer. The YAML 1.1 "bool" type resolves `y`, `Y`, `yes`, `Yes`, `YES`, `true`, `True`, `TRUE`, `on`, `On`, `ON` to true, and the matching `n`/`no`/`false`/`off` spellings to false ([YAML 1.1, type `tag:yaml.org,2002:bool`](https://yaml.org/type/bool.html)). `yamldecode`'s implementation (`zclconf/go-cty-yaml`, vendoring a YAML 1.1 parser) follows this table in full, including the bare single-letter `y`/`Y`/`n`/`N` forms (`resolve.go`'s `resolveMapList`, [`zclconf/go-cty-yaml`](https://github.com/zclconf/go-cty-yaml)); PyYAML's `SafeLoader` resolves `yes`/`no`/`on`/`off` the same way but not the bare `y`/`Y`/`n`/`N` forms, which it leaves as plain strings, and the prober's `config.py` refuses any of these spellings as a config fault ("must be true or false"). A file with `allow_allocation: y` therefore passed the Terraform guard, which read it as consent, while the prober's own `check-config` refused the identical file outright: the guard built to make consent reliable instead planned real capacity the prober itself would never run.

A fix that worked for this 1 spelling multiplied: a quoted key (`"allow_allocation": y`), a JSON-style flow mapping (`{"allow_allocation":y}`), an explicit `!!bool` tag, an inline anchor (`allow_allocation: &x y`), and an alias (`allow_allocation: *x`, which can point at a value defined anywhere else in the file) each needed their own raw-text regex, applied to the file with its comments stripped first (a comment that happens to contain one of these keys must not trip the check), because `yamldecode` had already thrown the original spelling away by the time any value-level check could see it. The regex grew with each round, with no principled stopping point: this family of input is YAML's whole grammar for scalar resolution, anchors, and aliases, and a hand-written regex over raw text can only ever cover the spellings someone thought to test. The guard was building a 2nd, independent YAML consent parser, in HCL, to agree with a Python one it could not call, for 1 pair of fields.

## Decision

### 1. Split the guard into 2 independent controls

1. **The per-job `allow_allocation` flag stays exactly where it already is**: in the experiment file, next to the job's own `simulate` key, checked only by the prober (`config.py`'s guard, `check-config`, and `run`). This is unchanged by this ADR. The key name stays `allow_allocation`; a later change may rename it, separately from this decision.
2. **Each Terraform stack gets its own input variable, `grant_billable_provisioning` (bool, default `false`)**, in place of the file-reading guard. This variable alone decides whether the stack creates or grants the rights that let something create or remove billable VMs, disks, NICs, or reservations:
   - AWS: the 4 `aws_odcr` IAM statements on `aws_iam_role_policy.prober` (`CreateAllocationProbeReservation`, `TagAllocationProbeReservationOnCreate`, `CancelAllocationProbeReservation`, `ReadAllocationProbeCapacity`) — the statements `var.enable_allocation_probe` gated before this change.
   - Azure: `azurerm_role_assignment.prober_capacity_allocator` and `azurerm_role_assignment.prober_subnet_joiner` (only when the subnet is also in another resource group). `azurerm_role_assignment.sweeper_cleanup` is deliberately **not** on this list; see item 3a, below.
3. The provisioning resources that Terraform itself plans (Azure's capacity reservation groups and scale sets) still follow the targets file's `provisioning_probes` entries for their shape — which regions, which SKUs, which scale sets — because that shape has nothing to do with consent; it is just a map of what the file lists. They plan only when `grant_billable_provisioning` is `true`: planning a scale set with no rights to scale it out is pointless, not a safety measure.
3a. **The sweeper's cleanup role assignment (`azurerm_role_assignment.sweeper_cleanup`) stays unconditional.** `grant_billable_provisioning` gates the rights that let something *create* billable capacity; `<prefix>-cleanup` (`azurerm_role_definition.cleanup`) is mostly read and delete, plus 3 write rights (`virtualMachines/write`, `virtualMachineScaleSets/write`, `virtualMachineScaleSets/scale/action`) that exist only so the sweeper can set a scale set to capacity 0. The sweeper code never creates a resource and never scales up: its only write call sets `sku.capacity` to 0 (`sweeper/azure/sweeper/azure_clients.py:111-113`, called from `sweeper/azure/sweeper/run.py:209`); every other call is a delete. The trade-off: the sweeper identity could, in principle, scale a set up. The project accepts that, because removing these rights would strand leaked capacity that only a scale to 0 can stop. Gating this assignment the same way as the other 2 would strand a leaked VM, disk, NIC, or prober-made reservation the moment an operator turns the grant off: nothing would be left able to delete it, and the leaked resource would keep billing. The rule: the grant controls creation, never deletion. Section 4, below, states the operator step this still requires before turning the grant off.
4. Terraform no longer reads the targets file for consent at all. `terraform_data.allocation_guard`, both its `lifecycle { precondition }` blocks (the consent check and the raw-text ambiguous-boolean check), `local.guard_entries`, `local.ambiguous_bool_literal`, the cross-cloud entry concatenation, and every `depends_on = [terraform_data.allocation_guard]` are removed from both stacks. The `tftest.hcl` runs and fixtures that existed only to prove the guard's raw-text parsing agreed with the prober's are removed with it. The shared fixtures that test the prober's own, unchanged consent guard (`prober/tests/fixtures/provisioning_guard*.yaml` and friends) stay: that guard did not change, only Terraform's copy of it is gone.
5. `experiment` still comes from the targets file only ([ADR 0010](0010-one-experiment-file-of-modules-and-jobs-with-a-billable-guard.md) section 2): this ADR does not touch that decision. There is still no `experiment_tag` variable.

### 2. Why 2 independent controls, not 1 shared one

A single control that both the stack and the prober read, kept in agreement by construction, is simpler to reason about than 2 that can disagree — when it works. The YAML divergence above is why it did not work: the only way to make the stack's reading of the file as strict as the prober's is a full, correct YAML 1.1 parser with alias resolution and PyYAML's own narrower bool table, which PyYAML provides to the prober, and which `yamldecode` does not provide, and cannot be made to provide, to Terraform's HCL expression language. Chasing exact agreement, 1 edge case at a time, is not a fixable bug; it is the design.

The 2 controls instead ask 2 different, independent questions, each answered by the party that can actually answer it:

- The per-job `allow_allocation` flag answers "did an experiment file author mean to run this specific job for real?" Only the prober needs to answer this, because only the prober reads a job from the file and decides whether to call a cloud API for it.
- `grant_billable_provisioning` answers "does this deployment's operator want this stack to be capable of provisioning real capacity at all?" Only the deployer answers this, once, when they set the variable (or do not) in their own `*.auto.tfvars` file. It needs no YAML parsing, because it is not a fact about the file; it is a fact about what the operator is choosing to deploy.

This also removes a class of risk the file-reading guard carried: a guard that reads the targets file is itself a 2nd place that must get every YAML edge case right, forever, as new ones are found. An explicit stack variable has no such surface. It is exactly as permissive as the 1 line that sets it.

### 3. The trade-off: the 2 controls can disagree

Because the controls are independent, a deployment can set them inconsistently. Each combination has a specific, intended outcome:

| `grant_billable_provisioning` | An active, consented job in the file | Outcome |
|---|---|---|
| `false` | No | Nothing plans, nothing runs. The safe default. |
| `false` | Yes | The stack plans no rights (and, on Azure, no provisioning resource for that job, section 1 item 3). The prober tries the call anyway, because its own guard passes (the job is consented); the call fails with the provider's error, written to the log as returned (for example `UnauthorizedOperation` on EC2 ([Error codes](https://docs.aws.amazon.com/AWSEC2/latest/APIReference/errors-overview.html)), or [`ResourceNotFound`](https://learn.microsoft.com/en-us/azure/azure-resource-manager/troubleshooting/common-deployment-errors) or [`AuthorizationFailed`](https://learn.microsoft.com/en-us/azure/role-based-access-control/troubleshooting) on Azure), because the role has no permission, or the resource the call names was never planned. **This is the intended, visible outcome of this mismatch, not a bug to route around.** It tells the operator, loudly, at run time, that the stack's grant and the file's consent disagree, instead of silently creating capacity nobody meant to grant rights for. |
| `true` | No | The stack grants rights (and, on Azure, plans the provisioning resources the file's shape calls for), but the prober makes no real call, because its own guard still gates on the job's `simulate`/`allow_allocation` keys. The deployment carries unused rights until the file also consents. This is a minor, accepted least-privilege gap: the alternative, denying rights until the exact moment a job needs them, is the file-reading guard this ADR removes. |
| `true` | Yes | Normal operation: the stack grants the rights, the prober's job is consented, the call runs for real. |

The project accepts the `false`/consented-job row's provider error (`UnauthorizedOperation` on EC2, `ResourceNotFound` or `AuthorizationFailed` on Azure) as the correct failure mode, in exchange for removing the YAML re-parsing risk in section 1 above entirely. Nothing can create real capacity without both an operator's explicit `grant_billable_provisioning = true` and a job author's explicit `allow_allocation: true`; the 2 together are still at least as strict as the single guard this ADR replaces, with no YAML ambiguity in whether that `true` holds.

### 4. Draining before disabling the grant, on Azure

`grant_billable_provisioning: true` to `false` removes `prober_capacity_allocator` (and `prober_subnet_joiner`, where it applies) in the same apply that removes the scale sets and capacity reservation groups: the prober loses the rights it needs to tear its own allocation down cleanly, in the same operation that can leave one half-torn-down. `sweeper_cleanup` stays (section 1 item 3a, above), so a leaked VM, disk, NIC, or reservation is not permanently stranded, but it is now reachable only by the sweeper, on the sweeper's own schedule (`FTG_MAX_AGE_SECONDS`, spec 0007), not by the prober's own, faster teardown path.

The operator step this implies: before switching `grant_billable_provisioning` from `true` to `false`, set every `azure.provisioning_probes` entry in the targets file to `simulate: true` first and deploy that change on its own. Wait until `make status/azure` shows 0 leaked resources (the line `leaked resources: 0`, which counts scale set instances, VMs, disks, NICs, and capacity reservations in the probe resource group) before applying the grant change or destroying the stack. Only then does turning the grant off remove rights that nothing still needs.

## Consequences

- `terraform/aws/variables.tf` and `terraform/azure/variables.tf` each add `grant_billable_provisioning` (bool, default `false`), in place of the removed `terraform_data.allocation_guard` (AWS already removed `enable_allocation_probe` earlier; this variable replaces it with the same shape, a different name, and the Azure stack gains the same kind of input for the first time).
- `terraform/aws/iam.tf` and `terraform/azure/probe.tf`/`rbac.tf` drop the guard resource, both preconditions, every `depends_on` on it, and gate the resources named in section 1 item 2 on `var.grant_billable_provisioning` directly.
- `terraform/aws/tests/allocation_guard.tftest.hcl` and `terraform/azure/tests/allocation_guard.tftest.hcl`, and the fixtures that existed only to drive them (`allocation_guard_ambiguous_bool.yaml`), are removed. New, smaller test runs cover `grant_billable_provisioning` directly: `false` plans no provisioning resource and neither billable-rights role assignment, regardless of the file, but still plans the unconditional `sweeper_cleanup`; `true` plans both billable-rights role assignments, following the file's shape.
- Specs 0003 (the per-job guard, unchanged in behavior, reworded to state plainly that Terraform does not read this key), 0004 and 0005 (the stacks: `grant_billable_provisioning`, the removed guard, the provider-error outcome row, `sweeper_cleanup` staying unconditional, the drain step of section 4, below), 0007 (notes that `sweeper_cleanup` stays unconditional, so the sweeper keeps its delete rights regardless of the grant), and 0010 (the Azure allocation probe spec's own mention of the guard) are updated in the same pull request as this ADR.
- A deployment must set `grant_billable_provisioning = true` explicitly wherever it wants a stack able to provision real capacity; everywhere else, including a signals-only deployment, it stays at its default `false`. No targets file content decides this any more.
- This supersedes [ADR 0010](0010-one-experiment-file-of-modules-and-jobs-with-a-billable-guard.md) section 7 and [ADR 0011](0011-store-and-per-job-simulate-replace-run-mode.md) section 3 rule 4's Terraform half and section 7 item 7 in full: the per-job consent flag these sections describe stays, read only by the prober; the Terraform guard they describe is removed and replaced by the variable in section 1 item 2, above.
